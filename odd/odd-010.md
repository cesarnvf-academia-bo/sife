# ODD-010: Sincronización de catálogos del SIAT desde Punto de Venta

## Objetivo

Agregar dos acciones nuevas en la pantalla **Punto de venta**:

1. **Sincronizar Catálogos**: invocar las 18 operaciones del servicio SOAP `FacturacionSincronizacion` cuyo nombre comienza con `sincronizar`, usando los datos de empresa, sucursal, punto de venta y CUIS vigente, y persistir la respuesta del SIAT en tablas nuevas.
2. **Mostrar Catálogo**: abrir un modal con un `select` de las 18 funciones y una tabla dinámica con los datos recibidos del SIAT para el punto de venta seleccionado.

La sincronización debe conservar historial: cada ejecución guarda su propia respuesta y sus propias filas de catálogo; la pantalla muestra los datos de la última ejecución exitosa por función.

## Contexto

- La ODD-009 implementó el CRUD de **Punto Venta**, la persistencia de **CUIS/CUFD** y las acciones por fila **Obtener CUIS** y **Obtener CUFD**.
- La infraestructura visual ya incluye:
  - `sife-modal` para formularios y ventanas emergentes.
  - `ToastServicio` para mensajes de éxito, error, información y advertencia.
  - `ConfirmacionServicio` con SweetAlert2 para confirmaciones de borrado.
- El proyecto ya contiene el contrato SOAP:
  - `partelogica/src/main/resources/wsdl/siat/FacturacionSincronizacion.wsdl`
  - `partelogica/src/main/resources/wsdl/siat/ServicioFacturacionSincronizacion.wsdl`
  - Cliente generado CXF en `bo.gob.impuesto.siat.sincronizacion`.
- La URL de referencia del contrato indicada para esta ODD es:
  - `https://pilotosiatservicios.impuestos.gob.bo/v2/FacturacionSincronizacion?wsdl`
- La configuración de ejecución ya existe y apunta al endpoint base, sin `?wsdl`:
  - `application.yml`: `siat.sincronizacion-url: https://pilotosiatservicios.impuestos.gob.bo/v2/FacturacionSincronizacion`
  - `PropiedadesSiat.sincronizacionUrl()`
  - Se mantiene ese patrón porque el cliente CXF ya está generado localmente; el sufijo `?wsdl` solo identifica el contrato, no la dirección SOAP de llamada.
- `ClienteSiatFactory.crearPuerto(...)` ya agrega el token por interceptor de salida y aplica timeouts, por lo que no debe modificarse.
- `SolicitudSincronizacion` requiere:
  - `codigoAmbiente` (`int`)
  - `codigoSistema` (`String`)
  - `codigoSucursal` (`int`)
  - `cuis` (`String`)
  - `nit` (`long`)
  - `codigoPuntoVenta` (`JAXBElement<Integer>`, opcional)
- `SolicitudSincronizacion` **no** incluye `codigoModalidad` ni token en el cuerpo SOAP.
- Todas las respuestas `sincronizar*` extienden `RespuestaConfiguracion`:
  - `transaccion: Boolean`
  - `mensajesList: List<MensajeServicio>` con `codigo: Integer` y `descripcion: String`
- El WSDL de sincronización **no** contiene `fechaVigencia`.

## Decisiones de esta ODD

1. Las dos acciones nuevas son **acciones por fila** de la tabla de Punto de venta y usan `puntoVenta.id` del registro seleccionado.
2. **Sincronizar Catálogos** ejecuta las 18 funciones en orden, de forma secuencial, en una sola petición HTTP.
3. El CUIS se resuelve **una sola vez** por ejecución:
   - Se busca el CUIS vigente en `cuis` para `(empresa_id = 1, puntoventa_id = id)`.
   - Si no existe o su valor está vacío, se obtiene con `ObtenerCuisServicio` y se persiste con `RegistroCuisServicio`.
   - El mismo CUIS se reutiliza en las 18 llamadas.
4. Si no se puede obtener el CUIS, la operación termina con `409` o `502` según corresponda y **no se registra ninguna ejecución de catálogo**.
5. Los códigos `codigoSucursal` y `codigoPuntoVenta` se obtienen desde `sucursal.codigo` y `puntoventa.codigo`; si no son numéricos, se lanza `ConfiguracionSiatInvalidaExcepcion` con el campo correspondiente.
6. No se envía `codigoModalidad` en `SolicitudSincronizacion`.
7. El token SIAT se envía únicamente mediante el interceptor existente en `ClienteSiatFactory`.
8. Se crea una fila en `sincronizacion_ejecucion` por cada función invocada, incluso cuando falla.
9. Si una función individual falla por `SiatNoDisponibleExcepcion`, se marca su ejecución como `FALLIDA`, se guarda el error y se continúa con las siguientes funciones.
10. Si `transaccion` es `false`, se guarda la ejecución como `FALLIDA`, se persisten los mensajes y no se insertan filas de catálogo.
11. Si `transaccion` es `true` pero la lista viene vacía, se guarda la ejecución como `EXITOSA` con cero filas de catálogo.
12. No se borran ejecuciones ni filas antiguas al sincronizar nuevamente.
13. Las 13 operaciones que responden `RespuestaListaParametricas` se guardan en **tablas separadas** para conservar la identidad de cada catálogo.
14. `sincronizarListaProductosServicios` guarda `nandina` como lista hija, una fila por valor, en `sincronizacion_producto_nandina`.
15. `sincronizarFechaHora` guarda el valor `fechaHora` en `sincronizacion_fecha_hora`, una fila por ejecución.
16. **Mostrar Catálogo** consulta siempre la última ejecución `EXITOSA` de la función seleccionada para `(empresa_id, puntoventa_id)`.
17. Si nunca se sincronizó una función, el modal muestra la tabla vacía y no lanza error.
18. El `select` de funciones se carga desde la parte lógica, no se duplica a mano en TypeScript.
19. Los mensajes de éxito/error de sincronización se muestran con `ToastServicio`.
20. Estas acciones no usan SweetAlert2; SweetAlert2 continúa reservado para confirmaciones de borrado.

    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    empresa_id BIGINT NOT NULL REFERENCES empresa(id),
    sucursal_id BIGINT NOT NULL REFERENCES sucursal(id),
    puntoventa_id BIGINT NOT NULL REFERENCES puntoventa(id),
    funcion VARCHAR(80) NOT NULL,
    estado VARCHAR(10) NOT NULL DEFAULT 'EXITOSA',
    transaccion BOOLEAN NOT NULL DEFAULT FALSE,

    fecha_hora_siat TEXT,

    ejecutado_en TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT ck_sinc_ejecucion_estado
        CHECK (estado IN ('EXITOSA', 'FALLIDA'))
);

CREATE INDEX idx_sinc_ejecucion_catalogo

### 3. Obtención del CUIS vigente

Agregar a `CuisMapper`:

```java
@Select no aplica: solo MyBatis XML
Cuis obtenerVigente(@Param("empresaId") Long empresaId,
                    @Param("puntoventaId") Long puntoventaId);
```

En `CuisMapper.xml`:

```sql
SELECT c.id,
       c.empresa_id AS empresaId,
       c.sucursal_id AS sucursalId,
       c.puntoventa_id AS puntoventaId,
       c.codigo_sucursal AS codigoSucursal,
       c.codigo_punto_venta AS codigoPuntoVenta,
       c.cuis,
       c.fecha_vigencia AS fechaVigencia,
       c.transaccion,
       c.mensajes,
       c.estado
FROM cuis c
WHERE c.empresa_id = #{empresaId}
  AND c.puntoventa_id = #{puntoventaId}
  AND c.estado = TRUE
  AND c.cuis IS NOT NULL
  AND btrim(c.cuis) <> ''
ORDER BY c.id DESC
LIMIT 1
```

`SincronizarCatalogosServicio` usa ese método antes de construir la solicitud:

- Si devuelve un `Cuis` con `getCuis()` no vacío, lo reutiliza.
- Si devuelve `null`, invoca `ObtenerCuisServicio.obtener(empresaId, codigoSucursal, codigoPuntoVenta)` y persiste con `RegistroCuisServicio.registrar(...)`.
- Nunca llama a `ObtenerCufdServicio` desde esta ODD.

### 4. `SolicitudSincronizacionServicio`

Responsabilidades:

- Cargar `Empresa` por `EmpresaServicio.EMPRESA_ID`.
- Validar, en este orden:
  1. Empresa existente → `EmpresaNoEncontradaExcepcion`.
  2. Token no vacío → `TokenSiatNoConfiguradoExcepcion`.
  3. `codigoSistema` no vacío → `ConfiguracionSiatInvalidaExcepcion(empresaId, "codigoSistema")`.
  4. `ambiente` numérico → `ConfiguracionSiatInvalidaExcepcion(empresaId, "ambiente")`.
  5. `nit` numérico → `ConfiguracionSiatInvalidaExcepcion(empresaId, "nit")`.
  6. `sucursal.codigo` numérico → `ConfiguracionSiatInvalidaExcepcion(empresaId, "sucursal.codigo")`.
  7. `puntoventa.codigo` numérico → `ConfiguracionSiatInvalidaExcepcion(empresaId, "puntoventa.codigo")`.
  8. CUIS no nulo/vacío → `SiatNoDisponibleExcepcion("FacturacionSincronizacion", "CUIS no disponible")`.
- Construir `SolicitudSincronizacion`:

```java
SolicitudSincronizacion solicitud = new SolicitudSincronizacion();
solicitud.setCodigoAmbiente(ambiente);
solicitud.setCodigoSistema(empresa.getCodigoSistema());
solicitud.setCodigoSucursal(codigoSucursal);
solicitud.setNit(nit);
solicitud.setCuis(cuis.trim());
solicitud.setCodigoPuntoVenta(
        new ObjectFactory().createSolicitudSincronizacionCodigoPuntoVenta(
                codigoPuntoVenta));
```

- `ObjectFactory` debe ser `bo.gob.impuesto.siat.sincronizacion.ObjectFactory`.
- No setear `codigoModalidad`.

### 6. `SincronizarCatalogosServicio`

Firma:

```java
@Transactional
public Long registrarEjecucion(...)

public SincronizacionResumen sincronizar(Long puntoVentaId)
```

Flujo de `sincronizar`:

1. `PuntoVenta puntoVenta = puntoVentaServicio.obtenerModelo(puntoVentaId);` → si no existe, `PuntoVentaNoEncontradoExcepcion` (`404`).
2. Resolver `Sucursal por sucursalMapper.findById(puntoVenta.getSucursalId())`.
3. Resolver CUIS vigente u obtenerlo una vez.
4. Construir `SolicitudSincronizacion` una vez.
5. Crear el puerto SOAP una vez.
6. Para cada `SincronizacionFuncion`:
   - Invocar.
   - Serializar `mensajesList` a JSON con `ObjectMapper`; si es `null`, usar `[]`.
   - Calcular `transaccion = Boolean.TRUE.equals(respuesta.isTransaccion())`.
   - Determinar `cantidadRegistros` según el tipo de respuesta.
   - Si `transaccion` es `true`, insertar ejecución `EXITOSA` y las filas del catálogo.
   - Si `transaccion` es `false`, insertar ejecución `FALLIDA` sin filas.
   - Si se lanza `SiatNoDisponibleExcepcion`, insertar ejecución `FALLIDA` con `error`, no insertar filas y continuar.
   - Agregar un `SincronizacionFuncionResultado` al resumen.
7. Devolver `SincronizacionResumen` con `total = 18`, `exitosas`, `fallidas` y `resultados` en el mismo orden del enum.

Notas:

- `sincronizar` **no** debe estar anotado con `@Transactional` porque incluye llamadas SOAP.
- `registrarEjecucion(...)` sí es transaccional y agrupa la ejecución con sus filas.
- La serialización de mensajes usa la misma forma JSON de ODD-009: `[{"codigo":926,"descripcion":"..."}]`.
